# Instructions

An **instruction** is the universal request format that user-facing FCC operations (signing a payment, verifying an attestation, generating a key, computing a VRF) all go through. The on-chain side validates the request, charges a fee, and emits an event; the off-chain layer (relay clients, TEE proxies) picks the event up and drives the actual operation through to completion.

The on-chain pieces:

- [`InstructionsFacet`](../../../contracts/tee/facets/InstructionsFacet.sol) — the public entry points.
- [`library/Instructions`](../../../contracts/tee/library/Instructions.sol) — the validation and dispatch logic, plus the system-instructions-sender registry.

## The instruction shape

```solidity
struct TeeInstructionParams {
    bytes32 opType;             // operation type (e.g. F_WALLET, F_VRF, F_FDC2, custom)
    bytes32 opCommand;          // command within the type (e.g. "PAY", "PROVE", "KEY_GENERATE")
    bytes   message;            // type/command-specific payload, ABI-encoded
    address[] cosigners;        // optional addresses required to additionally sign
    uint64  cosignersThreshold; // how many cosigners must sign (≤ cosigners.length)
    address claimBackAddress;   // where unspent fee gets refunded
}
```

Each on-chain `sendInstructions` call ends in a `TeeInstructionsSent` event:

```solidity
event TeeInstructionsSent(
    uint256 extensionId,
    bytes32 instructionId,
    uint32  rewardEpochId,
    TeeMachine[] teeMachines,
    bytes32 opType,
    bytes32 opCommand,
    bytes   message,
    address[] cosigners,
    uint64  cosignersThreshold,
    address claimBackAddress,
    uint256 fee
);
```

`instructionId` is either supplied by the caller (system path) or generated by the library:

```solidity
keccak256(abi.encode(extensionId, counter, blockhash(block.number - 1)))
```

where `counter` is per-extension and increments on every auto-generated instruction ID (i.e. whenever the library is called with `_instructionId == bytes32(0)`, which covers the regular `sendInstructions` path and any system send that doesn't supply its own ID).

## System operation-type prefix

Operations are split into two namespaces by the **first two bytes** of `opType`:

- **System operations** — `opType[0..2] == "F_"`. Reserved for FCC's own infrastructure: `F_WALLET` (key generate, delete, restore, sign payments), `F_VRF`, `F_FDC2`, `F_REG` (registration / attestation), `F_GET`, `F_POLICY`. Only **system instructions senders** (registered governance contracts) can dispatch system operations.
- **Custom operations** — anything else. Sent by registered extension instructions senders for their extension's specific operations.

The check is in [`Instructions.isSystemOpType`](../../../contracts/tee/library/Instructions.sol):

```solidity
bytes2 internal constant SYSTEM_OP_TYPE_PREFIX = bytes2("F_");
function isSystemOpType(bytes32 _opType) internal pure returns (bool) {
    return _opType[0] == SYSTEM_OP_TYPE_PREFIX[0] && _opType[1] == SYSTEM_OP_TYPE_PREFIX[1];
}
```

## Entry points

### `sendInstructions(_teeIds, _instructionParams)`

The general-purpose path on `InstructionsFacet`. The caller supplies an array of TEE IDs and the instruction params. The facet:

1. Deduplicates `_teeIds` (in place).
2. Resolves each ID to its `TeeMachine` struct via `MachineManager.getTeeMachine`.
3. Authorizes the caller — see below.
4. Calls `Instructions.sendInstructions(bytes32(0), teeMachines, _instructionParams)`. The first arg `bytes32(0)` means "auto-generate the `instructionId`".

**Caller authorization**:

- If the caller is a registered **system instructions sender** (`Instructions.isSystemInstructionsSender(msg.sender)`), the call is allowed unconditionally.
- Otherwise, the caller must be the **extension's** `instructionsSender` (configured via `ExtensionManagerFacet.setExtensionContracts`). The opType must not be a system opType (extensions cannot dispatch under the `F_` namespace); enforced by `SystemOpTypeNotAllowed(opType)`.

### `sendSystemInstructions(_instructionId, _teeIds, _instructionParams)` and the `TeeMachine[]` overload

Restricted to registered system instructions senders. Used by FCC's own contracts (e.g. `Fdc2Hub.requestAttestation`, `TeePayments`) when they need to send a system operation. Accepts a caller-supplied `_instructionId` (so an upper layer can deterministically derive IDs) or `bytes32(0)` to auto-generate.

### `registerSystemInstructionsSenders` / `unregisterSystemInstructionsSenders`

Governance-only. Add or remove addresses from the system-instructions-senders set. Members of this set can call `sendSystemInstructions` and can also bypass the per-extension authorization check on `sendInstructions`.

## Validation and fee

Inside `Instructions.sendInstructions` (the library function), every instruction goes through:

1. `_teeMachines.length > 0`, `opType != 0`, `opCommand != 0`, `message.length > 0`, `cosignersThreshold ≤ cosigners.length` — basic shape checks.
2. Resolve `extensionId = MachineManager.getExtensionId(_teeMachines[0].teeId)`.
3. Require the extension is not currently emergency-paused: `!MachineEmergencyPause.isExtensionEmergencyPaused(extensionId)` (`EmergencyPauseActive(extensionId)` if it is). This is the single chokepoint through which the per-extension overlay blocks every dispatch path — both regular and system opTypes are rejected. See [Machine Lifecycle / Emergency pause](./MachineLifecycle.md#emergency-pause).
4. For each subsequent machine, require its `extensionId` matches the first (`ExtensionIdMismatch()` if not).
5. For non-system opTypes, require each machine's status is `PRODUCTION` (`TeeMachineNotAvailable()` if not). For system opTypes, **status is not checked** — system operations can target machines in `INITIALIZED` state (this is how the registration availability check works — the machine is still `INITIALIZED` when the first attestation request goes out).
6. Compute the fee: `OperationFees.calculateFeeByTeeIds(opType, opCommand, teeIds)` — see [Operation Fees](./OperationFees.md).
7. Require `msg.value >= fee` (`FeeTooLow()` if not).
8. Forward `msg.value` (the entire amount, not just the fee) to `RewardManager.receiveRewards{value: msg.value}(currentRewardEpochId, false)` as a community offer for the current reward epoch.
9. Emit `TeeInstructionsSent`.

**The whole `msg.value` goes to `RewardManager`** — there is no automatic refund of the difference between `fee` and `msg.value`. If a caller pays more than the fee, the surplus stays in the reward pool. Application contracts that want to forward exactly the fee should call `OperationFees.calculateFeeByTeeIds` first.

The `claimBackAddress` field is used by the off-chain layer for things like FDC2's per-instruction unspent-fee return — the diamond's role here is just to record it in the event so the off-chain contract knows where to send any refund.

## Instruction ID generation

```solidity
keccak256(abi.encode(extensionId, counter, blockhash(block.number - 1)))
```

The counter is per-extension. `blockhash(block.number - 1)` is the previous block's hash — adding it to the seed prevents trivial pre-computation of future instruction IDs by an attacker that knows the counter. Note: `blockhash` for blocks more than 256 in the past returns zero, but since the value is consumed in the same block as the call, this is always live.

Two callers in the same block in the same extension would have the same `blockhash` input but different `counter` values, so IDs remain unique.

## What happens after the event

`TeeInstructionsSent` is what the off-chain layer subscribes to. From there:

1. Each registered relay client signs the canonical encoding of the instruction (with its FSP signing-policy address) and forwards it to each `TeeMachine[i].teeProxyId`.
2. The TEE proxy verifies the relay client's signature against the FSP signing policy. It accumulates signatures until the threshold (signing-policy threshold for ordinary operations, or per-instruction `thresholdBIPS` for FDC2 / extension operations) is reached.
3. If `cosigners.length > 0`, the proxy also collects cosigner signatures. `cosignersThreshold` of them must arrive.
4. With both thresholds met, the proxy hands the instruction to the TEE for execution. The TEE returns a signed action result.

The on-chain side has nothing more to do unless / until the action result is submitted back. Different operation types have different "submit back" paths:

- **FDC2 attestations** end up in a consumer contract that calls `Fdc2Verification.verifyTeeSignatures` / `verifySigningPolicySignatures` to validate the response — see [FDC2](../FDC/Fdc2.md).
- **PMW XRPL payments** are signed transactions — they're broadcast on XRPL directly, no on-chain follow-up on Flare needed.
- **Key generations and deletions** post their results back via dedicated facet methods (`WalletKeyManagerFacet`).

The instruction primitive is intentionally generic: the on-chain layer doesn't know what `F_WALLET / PAY` *means*; it just routes the request to the right TEEs and lets them execute the application-specific logic.

## Why send the whole `msg.value` to `RewardManager`

Routing 100% of the paid value into `RewardManager` (rather than refunding excess) keeps the on-chain contracts simple and prevents griefing where the diamond holds dust ETH balance. The off-chain reward-calculation layer can decide to attribute "excess" payments back to the originator if appropriate — it sees the original `fee` and the actual `msg.value` in the event. Most callers shouldn't overpay anyway since `OperationFees.calculateFeeByTeeIds` is cheap to call.

## Where each system opType lives

| System `opType` | Originator | Purpose |
|-----------------|------------|---------|
| `F_REG` | `MachineManagerFacet` | TEE attestation requests (initial / re-attestation) |
| `F_WALLET` | `WalletKeyManagerFacet`, `WalletManagerFacet` | Generate / delete / restore keys; sign XRPL transactions |
| `F_VRF` | `VrfFacet` | VRF proof generation |
| `F_FDC2` | `Fdc2Hub` (external — registered as system instructions sender) | FDC2 attestation requests |
| `F_GET` | various | Read-only queries to TEEs (e.g. fetch backup material) |
| `F_POLICY` | `MachineManagerFacet`, `ExtensionGovernanceFacet` | Policy initialization / update |

The full catalog of system commands lives in [flare-specs/FCC/Commands](https://github.com/flare-foundation/flare-specs/tree/main/src/FCC/Commands).
